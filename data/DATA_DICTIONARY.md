# Data dictionary

Generated by `python tools/export_csv.py`. `data/sources.json` holds the SHA-256 of every input file and of each CSV,
so every row can be traced back to a logged run (`run_id`, `observed_at_utc`).

| File | Real or synthetic | What it is |
|---|---|---|
| `real_crypto_observations.csv` | **Real** | Crypto found in two public repositories at pinned commits, plus live TLS 1.3 handshakes with two public endpoints |
| `real_banks/targets.csv`, `real_banks/scan_<date>.csv` | **Real** | One TLS handshake with each of 60 public Indian bank endpoints (CC0 dataset, pinned). See `real_banks/DATA_DICTIONARY.md` |
| `SYNTHETIC_mock_bank_assets.csv` | **Synthetic** | The fictional 16-asset mock-bank inventory the demo schedules. All names are invented. Not real data |

What is *not* here:
- **Lab handshakes.** These are real TLS 1.3 handshakes with local services on 127.0.0.1 that use lab certificates. They are regenerated on every run (`out/capture.json`).
- **Risk, effort and shelf-life values.** These are assumptions in `config/assumptions.json`, not measurements.

## real_crypto_observations.csv

One row per observation. `record_type` says which columns apply. Empty means "not applicable to this record type".

| Column | Meaning | Unit / values | Source |
|---|---|---|---|
| record_type | `static_finding` (code/config scan) or `live_handshake` (TLS probe) | enum | tools/export_csv.py |
| source_name | Repository name, or reference-endpoint id | text | detect/real_repos.json; config/atlas_web.json `reference_endpoints` |
| source_url | Repository clone URL, or endpoint URL | URL | same |
| source_commit | Pinned git commit that was scanned (static_finding only) | 40-hex SHA-1 | detect/real_repos.json |
| observed_at_utc | When the scan or handshake ran | ISO 8601 UTC | `ts` of the run |
| run_id | Run that produced the row | 32-hex | out/real_repos/*.json, workspace out/detect.json |
| file | File inside the repository | repo-relative path | static scan |
| line | Line number of the match | integer, 1-based | static scan |
| rule | Detection rule that matched | rule id (detect/rules.py) | static scan |
| crypto_family | Algorithm family: RSA, ECC, DH, DSA, PQC, or UNKNOWN (TLS on library defaults; needs a live probe) | enum | static scan; probe `kex_family` |
| use | What the crypto is used for: `kex` (key exchange), `sig` (signatures/certificates), `both` | enum | static scan; `kex` for handshakes |
| confidence | Rule confidence | high / medium / low | detect/rules.py |
| quantum_vulnerable | Breakable by a large quantum computer (Shor). Covers the family for findings and the negotiated key exchange for handshakes. `unknown` = needs a live probe | true / false / unknown | detect/inventory.py `VULNERABLE` = RSA, ECC, DH, DSA |
| endpoint | Host:port probed | host:port | detect --probe |
| tls_protocol | Negotiated protocol | e.g. TLSv1.3 | openssl s_client -brief |
| key_exchange_group | Negotiated key-exchange group (X25519MLKEM768 = hybrid post-quantum) | IANA group name | openssl s_client -brief |
| cipher | Negotiated cipher suite | IANA name | openssl s_client -brief |
| cert_algorithm | Server certificate key algorithm | e.g. RSA-2048, ECDSA-secp256r1 | openssl s_client |
| handshake_transcript_sha256 | SHA-256 of the recorded handshake messages. This is evidence that the handshake happened; no keys and no traffic are recorded | 64-hex | detect/live_probe.py |

Probes use OpenSSL 3.6.5 and offer `X25519MLKEM768:X25519:prime256v1`. A classical result means the server chose classical
key exchange. No traffic was decrypted.

## real_ibm_qaoa/ (REAL, IBM Quantum hardware)

Written by `python tools/export_ibm_run.py` from a logged `python -m qaoa --ibm` run (`out/results.json`,
`out/schedule.json`, `config/qaoa.json`, `runs/<run_id>/ibm_p*.json`, `runs/platform_jobs.log`, `out/ledger.jsonl`);
nothing is typed by hand. Imported on another machine, without IBM access, by `python -m qaoa --ibm-import
data/real_ibm_qaoa`. A measured cross-check against the exact optimum; no quantum advantage claimed. Checked by
`tests/test_real_ibm_qaoa.py` and `tests/test_qaoa_ibm_import.py`.

| File | Contents |
|---|---|
| run.json | run_id, executed_at (UTC), schedule SHA-256, backend, job IDs, ledger entry on the executing machine |
| schedule.json | byte copy of the `out/schedule.json` the QUBO was built from |
| qaoa_config.json | byte copy of `config/qaoa.json` used for the run |
| problem.json | candidates (assets, values, weights, capacity, dependencies, shrink log), the QUBO (offset, linear, quadratic terms) and the exact optimum |
| angles.json | simulator-tuned gammas, betas and energy scale per p: the circuits that were sent to IBM |
| jobs/ibm_p&lt;p&gt;.json | per job: IBM job ID, backend, shots, raw counts (qubit 0 rightmost), transpiled depth, 2-qubit gate count and names, op counts, physical-qubit layout, optimization level and seed, QPU seconds, submit / job-ID-logged timestamps |
| metrics.json | metrics computed at run time for ibm, local, qpiai_local and random, and the comparisons (z-scores) |
| qaoa_section.json | the full `out/qaoa.json` section of the run |
| table.csv | `qaoa.table` rows, flat: metrics (`feasible_fraction`, `best_feasible_objective`, `approximation_ratio`, `energy_ratio`, `p_optimal`, `p_optimal_assets`) and for IBM rows `hw_job_id`, `hw_backend`, `hw_transpiled_depth`, `hw_two_qubit_gates`, `hw_qpu_seconds` |
| versions.json | Python, OS and package versions of the executing machine |
| manifest.json | SHA-256 of every file above |

`hw_transpiled_depth` and `hw_two_qubit_gates` describe the circuit actually sent to the QPU (after transpiling to
the backend's native gates); `hw_qpu_seconds` is IBM's reported usage for the job.
